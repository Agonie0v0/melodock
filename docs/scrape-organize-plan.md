**MeloKeep 原生刮削、整理、入库方案**

历史规划（2026-10-23）。当前范围已按用户要求扩展为 V2 的刮削整理能力，以下初期范围不再作为当前限制。当前功能与验证边界见 [V2 刮削整理功能对照](v2-scraping.md)及[音乐库使用说明](music-library.md)。未操作用户的真实曲库。

**结论与已确定的方向**

可行。按用户已确认的要求，继续采用 MeloKeep 单独部署，在现有项目中原生实现下载后的元数据补全、文件整理和曲库入库。Music Tag Web V2 用作功能与交互参考，不依赖其容器、激活服务或私有接口。

目标不是一次复制 V2 的整个音乐服务器，而是先让“下载 → 刮削 → 整理 → 入库 → 播放/通知”成为可靠的自动流程，再扩展历史曲库批处理。第一期应保留完整下载引擎和所有现有音源，不改变原有搜索、解析、续传与机器人入口。

| 路线 | 收益 | 代价与边界 | 本项目选择 |

**4. 用户使用流程**

在设置中启用“下载后自动整理”，选择刮削源、需要补全的字段、目录规则和低置信度处理方式。用户继续从网页、歌单导入或机器人下载；任务中心展示每个处理阶段。高把握的结果自动入库，无法确定版本的结果进入“待确认”。

```mermaid
flowchart LR
    A[搜索 / 歌单 / 机器人] --> B[下载到任务暂存目录]
    B --> C[文件校验与持久化交接]
    C --> D[读取原标签和下载来源]
    D --> E[补全检索与版本匹配]
    E --> F{匹配是否可靠}
    F -->|是| G[写标签与歌词封面]
    F -->|否| H[待确认 / 保留原文件]
    H -->|确认候选| G
    G --> I[整理预览与安全归档]
    I --> J[更新本地曲库索引]
    J --> K[播放 / 通知 / 可选外部扫描]
```

这里的“入库”首先指更新 MeloKeep 自己的曲库索引，歌曲在当前播放器中可搜索、收藏和播放。Navidrome/Jellyfin 等外部媒体库刷新作为可选扩展；外部扫描失败不回滚已经完成的本地入库，也不能标成外部已入库。

**5. 功能范围与优先级**

| 能力 | 第一阶段：自动闭环 | 第二阶段：历史曲库 | 后续按需 |
| --- | --- | --- | --- |
| 下载后自动处理 | 启用开关、持久化任务、失败重试 | 规则重跑、批次报告 | 定时导入外部目录 |
| 标签补全 | 标题、歌手、专辑、封面、歌词；来源有值时补年份/曲序/碟号/专辑歌手/流派 | 完整批量编辑、字段锁定 | 更广的扩展标签 |
| 匹配 | 来源 ID 优先、标题/歌手/专辑/时长/版本比较；低把握待确认 | 多候选对比、人工指定来源 | 音频指纹辅助识别 |
| 音频格式 | 优先验收 MP3、FLAC、M4A；其他现有格式保持可用，未经验证不自动改写 | 分格式扩展 OGG/OPUS/WAV/APE 等 | DSD、整轨等专门支持 |

V2 的后台刮削本身也采用新增目录处理与归档，官方去重功能强调先输出检查结果，再由用户决定删除；本方案借鉴这种可控的操作方式。[后台刮削](https://xiers-organization.gitbook.io/music-tag-web-v2/gong-neng-miao-shu/hou-tai-gua-xiao) · [去重说明](https://xiers-organization.gitbook.io/music-tag-web-v2/gong-neng-miao-shu/yin-yue-qu-zhong)

**6. 刮削与匹配策略**

按“已知来源 → 已有标签 → 缺项检索”的顺序处理，减少重复请求与错配。

1. 下载成功后读取最终文件标签，并保存来源平台和歌曲 ID。当前下载工作进程主要返回文件路径，需扩展为逐文件返回不含 Cookie/签名 URL 的元数据摘要；多集下载不能把父任务信息套到每个文件。
2. 同一来源、同一歌曲 ID 的有效信息优先使用；不因为另一个来源封面更大就替换整个专辑信息。
3. 缺失字段再检索候选。优先评估现有网易云、QQ 等音源中可稳定取得元数据的部分，最终启用名单由样本实测确定。复用现有代理、Cookie 与超时设置，但分别提供“下载音源”和“刮削来源”开关。
4. 做元数据查询时，不应为了获得年份等字段强制解析可下载音频 URL；现有搜索中与下载可用性绑定的过滤需要拆开，避免有元数据却因无下载权限而被过滤。
5. 匹配同时比较标题、歌手、专辑、时长以及 Live/Remix/伴奏/翻唱等版本特征。缺少信息不能算作一致，版本矛盾不能被标题相似度抵消；多个候选接近时转人工确认。
6. 先用有标注的样本确定自动接受阈值，分数仅是匹配依据，不能展示成未经校准的“正确率”。只有标题一致不允许覆盖全套标签。
7. 默认只补空值；显式勾选覆盖时才替换已有字段。用户手动修改过的字段标记锁定。候选选定后保存字段来源、匹配理由和处理规则版本。
8. 歌词与封面可以单独补全，但必须属于已确认的歌曲/专辑版本。封面限制大小与格式，不让错误资源使音频任务整体丢失。

音频指纹识别放到后续：它需要额外组件、服务或密钥，也不保证获得完整中文音乐元数据；无法匹配时仍需保留人工确认入口。

**7. 文件、身份和任务可靠性——必须先做好**

当前 `library_file()` 使用文件路径计算 `local-...` 曲目 ID，下载任务的 `file` 也保存路径 token。整理造成路径变化后，现有收藏、歌单、播放地址和机器人链接可能失效。不能只在下载回调里加一个移动文件操作。

- 增加稳定的 `asset_id`，与当前路径分离；每个物理音频文件一个 ID，线上歌曲来源 ID 单独保存。路径变化只更新映射，播放/下载通过 ID 解析最新路径。
- 迁移现有本地曲目时保留旧 ID 别名，更新收藏、播放列表、已保存歌单及下载记录中的引用；旧链接解析兼容别名。已经发出的签名链接需要检查签名载荷并保留兼容解析。
- 任务保存输入文件版本、规则版本、当前阶段、错误、输出路径及重试次数。同一个文件版本和同一规则的重复提交不会重复移动或重复通知。
- 保留下载状态，另加处理状态：`queued → identifying → tagging → organizing → indexing → complete`，另有 `needs_review / failed / cancelled`。下载成功、刮削失败是两个独立结果。
- 下载文件先持久化交接到未被正式曲库扫描的待处理区，再释放下载任务。网络刮削不占用全局下载锁；处理池先设小并发，复用现有 SQLite，不新增 Redis/Celery 服务。
- 交接成功前不清理唯一文件；恢复时区分下载未完成和处理未完成，禁止为刮削失败重新下载音频。
- 对正在播放、删除、编辑的文件采用每文件互斥和输入版本校验。发现用户在预览后修改了文件，重新预览而不是覆盖。
- 修改在工作副本上完成，校验可读取和标签结果后发布；原文件按可配置的保留时间/空间预算保存，至少在操作提交前不得删除唯一原件。
- 文件系统移动与 SQLite 更新不是同一个事务：先记录操作意图，再发布文件，最后提交路径/任务记录；启动时依据操作日志检查并补齐中断步骤。
- 同文件系统使用安全替换/重命名；跨挂载点采用目标目录临时副本、校验、再发布，成功记录后才处理源文件。预留磁盘空间检查。
- 重名默认保留双方或跳过，不自动覆盖。音频、LRC、同名封面作为同一操作管理；专辑共享 `cover.jpg` 有独立冲突规则。
- 限制处理目录和模板输出范围，拒绝路径穿越、越界符号链接及 Windows 保留名；在 Docker/NAS 上检查实际 UID/GID 权限。

建议沿用 `/music`、`/data` 两个挂载：`/music/.partial` 下载中，`/music/.processing` 待处理/工作副本，`/music/.originals` 临时恢复副本，`/music/library` 最终曲库。内部扫描必须明确排除前三个目录；外部音乐服务器仅挂载最终曲库。现有文件不强制批量迁移，历史整理需预览后应用。

示例整理模板：`{album_artist}/{album}/{track_number} - {title}.{ext}`。专辑歌手缺失时回退到歌曲歌手，缺少曲序时省略序号；多碟专辑按碟号分目录。合集、多个歌手、同名不同版本都必须有固定规则。

**8. 需要改动的模块**

下列是职责划分，不要求为每个职责都新建类或框架。

| 文件/区域 | 计划改动 |
| --- | --- |
| `engine_api.py` | 下载完成交接、处理 API、事务存储辅助函数、稳定文件 ID 解析、旧路径兼容 |
| `engine_worker.py` | 按文件返回下载结果与必要来源元数据，继续保留完整原引擎 |
| `local_library.py` | 扩展标签模型、MP3/FLAC/M4A 格式映射、封面与歌词写入、修改差异和安全发布 |
| 新增 `metadata_scraper.py` | 来源结果归一化、候选匹配、字段合并；优先包装现有能力 |
| 新增 `library_pipeline.py` | 持久化阶段调度、整理计划、执行日志、恢复、入库；首期避免再拆服务 |
| `bot_notifications.py` | 区分下载成功/处理完成/待确认，发送前解析最终文件位置，防止阶段重复通知 |
| `frontend/src/MusicLibrary.tsx`、`App.tsx`、`types.ts`、`api.ts` | 展示阶段与异常、批量入口、差异/路径预览、候选确认与重试 |
| 设置页面与配置接口 | 自动处理开关、字段覆盖、来源优先级、目录规则、原件保留策略 |
| `Dockerfile`、部署文档 | 包含新增模块，明确目录和权限；首期沿用现有 Mutagen/FFmpeg |

存储先复用现有 SQLite `records`，新增文件、处理任务和操作日志记录类型；涉及多个记录的提交必须放在一个事务中。若批量曲库实测证明 JSON 记录和现有 10000 条读取上限成为瓶颈，再增加专用索引表和分页查询；不能以现有上限宣称支持任意规模曲库。

建议业务接口为“创建处理任务、查询任务、预览标签与路径、确认候选、应用计划、重试、恢复”。这些是拟新增的 MeloKeep API，具体 URL 随实现确定，并非声称 V2 已提供对应接口。每个预览附输入版本，应用时重新校验。

**9. 界面上的最终形态**

- 下载列表直接显示“下载完成，正在补全标签”“待确认版本”“已整理入库”；展开显示本次修改、来源及最终目录。
- 本地音乐库增加“刮削”“整理”“批量编辑”，展示修改前后标签和文件路径；操作按钮只对所选文件生效。
- 任务中心按处理中、待确认、失败、已完成筛选，可只重试失败阶段；不显示没有依据的百分比。
- 设置保留一个清晰的自动化入口；高级选项收起。外部刮削平台不可用时能看到具体字段失败，不把已经下载的文件标成下载失败。
- 机器人默认在流水线结束后发送最终文件；进入待确认/处理失败时提供原文件和明确状态，避免用户无限等待。通知去重与现有渠道行为一起回归测试。

**10. 实施顺序与验收门槛**

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| A：数据和文件基础 | 稳定 ID、旧引用迁移、持久化处理任务、预览/操作日志与恢复 | 重命名后收藏/歌单/播放/机器人链接仍可解析；进程中断后能恢复 |
| B：最小自动闭环 | MP3/FLAC/M4A 标签补全、候选确认、安全归档、入库与统一状态 | 网页、歌单、机器人下载均能自动进入同一流程；失败不丢原文件 |
| C：历史曲库整理 | 目录批处理、批量标签、文本清理、重复候选、批次恢复 | 大批任务可分页查看；先预览后应用；冲突可跳过而不阻塞整批 |
| D：可选增强 | 指纹识别、更多格式、外部扫描、CUE 分轨/转码 | 每项独立验收、可关闭，不改变已稳定的主流程 |

第一版发布范围是 A+B。C、D 单独安排，避免第一版变成一次完整的音乐服务器重写。

拟采用以下验收样本与故障用例；数量是测试计划，不是已经取得的测试结果：

1. 至少 30 首人工标注样本，覆盖准确来源 ID、缺失标签、同名不同歌手、Live/Remix、中文多歌手、合集和多碟；验收重点是高把握自动处理、歧义转人工，不许为了自动化率强配。
2. MP3、FLAC、M4A 标签写入后能重新读取；音频有效载荷或解码后的音频校验保持一致。整个文件哈希会因改标签变化，不能用它判断音频被转码。
3. 在交接、写标签、移动文件和数据库提交之间分别中断进程，重启后不重复产生文件、不删除唯一原件、不丢失任务。
4. 同名文件、并发重复任务、磁盘不足、无写权限、NAS 跨挂载移动、播放中文件被占用、封面下载失败、歌词缺失均有可恢复结果。
5. 标签/路径更新后，收藏、播放队列、已保存歌单、下载记录和机器人签名链接完成兼容检查。
6. 处理功能关闭时，原下载布局、暂停续传、全部动态音源、网页和机器人流程保持通过现有测试。
7. 历史目录先以 100 首混合样本验证批处理与恢复，再按实际曲库规模测量扫描耗时和内存；没有实测前不承诺性能指标。

**11. 仍需在开发阶段验证的事项**

元数据源能否稳定提供额外字段、音源接口限流情况、不同音频容器对标签的保存差异、NAS 文件系统行为，以及现有签名链接的完整迁移路径，都需要针对实际代码和样本验证。它们影响功能覆盖和实现细节，不影响单应用原生实现这条路线的基本可行性。

最终建议：以现有下载链路为基础，先实现 A+B；核心投资是稳定文件身份、安全操作与可信匹配。完成后，用户的一次下载即可产出整理好的本地曲库文件，全程在 MeloKeep 内查看和处理。
